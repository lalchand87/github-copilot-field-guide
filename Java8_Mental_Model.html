◉Mental Model

The One Mental Model

A stream is a pipeline. Every problem = Source → Transform → Aggregate What do I have? → Source What do I want to do? → Intermediate ops What do I want back? → Terminal op A stream holds NO data — it is a plan over a source, executed ONCE, on demand.

The 3-Question Framework

Ask before writing a line1. WHAT element type flows through? Employee, Integer, Transaction… 2. WHAT transformation? filter, map, flatMap, sorted, distinct, grouped… 3. WHAT do I collect into? List, Map, single value, boolean + one clarifying Q: dups? null keys? ordering? scale? → sounds senior.

◈The 6 Problem Patterns

1 · Filter + Collect

// names in Eng, salary > 80k employees.stream() .filter(e -> "Eng".equals(e.dept())) .filter(e -> e.salary() > 80_000) .map(Employee::name) .collect(toList());

2 · Group + Aggregate

// max earner per dept (name only) .collect(groupingBy(Emp::dept, collectingAndThen( maxBy(comparingDouble(Emp::salary)), o -> o.map(Emp::name).orElse("none"))));

3 · Sort + Slice

// 2nd-highest DISTINCT value .map(Emp::salary).distinct() .sorted(reverseOrder()) .skip(1).findFirst(); // sorted = O(n log n) — for top-K use a // bounded heap O(n log k). Clarify // "distinct value vs rank" first.

4 · Flatten + Process

// all settled txns across accounts accounts.stream() .flatMap(a -> a.getTxns().stream()) .filter(t -> "SETTLED".equals(t.status())) .mapToDouble(Txn::amount) .sum();

5 · Partition

// split high / low earners .collect(partitioningBy( e -> e.salary() > 70_000)); // → Map<Boolean, List<Emp>> .collect(partitioningBy(p, counting())); // always BOTH keys present

6 · String Ops

// first non-repeating char — Unicode-safe str.codePoints() // not chars()! .mapToObj(Character::toString) .collect(groupingBy(identity(), LinkedHashMap::new, counting())) .entrySet().stream() .filter(e -> e.getValue() == 1) .map(Map.Entry::getKey).findFirst();

⚡Internals & Laziness

How a Stream Executes

Source = Spliterator (tryAdvance, trySplit → basis of parallelism).
Lazy + fused: intermediate ops build a chain of Sinks; nothing runs until a terminal op pulls elements through in one pass — no intermediate collections.
Short-circuit: limit / findFirst / anyMatch / takeWhile cancel traversal early → safe on infinite streams.
peek may be elided: count() can skip the whole pipeline (Java 9+).

reduce, Properly

reduce(identity, accumulator, combiner) words.reduce(0, (acc,w) -> acc + w.length(), // U×T→U (a,b) -> a + b); // U×U→U
3 laws (break → parallel goes wrong): identity (id op x = x), associativity (sub/div fail), compatibility.
Combiner runs ONLY in parallel — bugs hide in sequential tests.

reduce vs collect · Collector

reduce = immutable reduction (values). String via a+b is O(n²).
collect = mutable reduction (containers) — the right tool for List/Map/StringBuilder.
Collector = 5 fns: supplier · accumulator · combiner · finisher · characteristics (IDENTITY_FINISH, UNORDERED, CONCURRENT). Write your own with Collector.of(…).
⇉Parallelism & Correctness

Parallel — Wins vs Backfires

Use parallel whenAvoid when
large N × non-trivial worksmall N, or tiny per-element work
splits cheap+even: array, ArrayListLinkedList, iterate, BufferedReader.lines
CPU-bound, independentblocking I/O, locks, DB calls
stateless, cheap to combinesorted/distinct/limit barriers
Rule of thumb: N × Q (size × cost-per-element) ≳ 10,000. Amdahl: tiny work never amortises fork/join overhead — often slower than sequential.

The Footgun + Correctness Rules

commonPool footgun: every parallel stream shares ONE pool (cores−1). A blocking call starves all of them — process-wide. Never block in a parallel stream; isolate in your own ForkJoinPool if you must.
3 correctness rules:
1. No shared mutable state (collect, don't forEach(list::add)).
2. Associative, stateless lambdas (reduce-with-subtract is wrong).
3. A correct combiner (untested by sequential runs).
Ordering: findAny > findFirst · forEachOrdered preserves order · .unordered() speeds distinct/limit.
◎Judgment, Performance & Quick Ref

When NOT to Use Streams

Prefer a loop when: hot inner loop (lambdas/Spliterator allocate; loops are JIT-friendlier) · need index mutation / complex break · checked exceptions · a loop is simply clearer · you need a clean stack trace.
A stream is not a goal. Use it for clear bulk transformation, not as a hammer.
Money: never double — BigDecimal + reduce. (summingDouble uses Kahan sum but binary≠decimal.)

Primitive Streams & One-Pass

count+sum+min+max+avg in ONE passDoubleSummaryStatistics s = emps.stream() .mapToDouble(Emp::salary) .summaryStatistics(); s.getCount(); s.getSum(); s.getAverage();
IntStream/LongStream/DoubleStream avoid boxing (GC). boxed() at the boundary.
Checked exceptions don't fit lambdas → handle inside, wrap unchecked, or use a loop.

Key Rules to Never Forget

1. distinct() before sorted() for Nth highest — but clarify value vs rank.
2. LinkedHashMap::new in groupingBy when key order matters.
3. flatMap when the fn returns a Stream/Optional.
4. orElseGet (not orElse) for expensive defaults.
5. toMap always needs a merge fn; NPEs on null values.
6. Streams are lazy + single-use.
7. sorted/distinct/limit are stateful — buffer, break infinite, cost in parallel.
8. reduce's 3-arg combiner runs only in parallel.
9. Parallel = no shared state + associative + correct combiner; never block.
10. codePoints() not chars() for Unicode.
11. IntStream/summaryStatistics to avoid boxing & aggregate in one pass.
12. For money: BigDecimal + reduce, never double.
