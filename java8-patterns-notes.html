01. Lambda Expressions

A lambda is a name-less block of code you can pass around like a value — it exists purely to fill the single abstract method of a functional interface (an interface with exactly one unimplemented method). Java 8's whole feature set is built on this one idea.

Anatomy of a lambda

(Employee e) -> e.salary() > 80000
 ─────┬─────    ─────────┬─────────
   parameters            body (expression or { block })
Parameter types are usually inferred, so (e) -> e.salary() > 80000 or even e -> e.salary() > 80000 (parens optional for a single untyped parameter) all compile identically.

Evolution — same sort, three eras of Java:

StyleCode
Anonymous class (pre-Java 8)list.sort(new Comparator<Employee>(){ public int compare(Employee a, Employee b){ return Double.compare(a.salary(), b.salary()); }});
Lambda (Java 8)list.sort((a, b) -> Double.compare(a.salary(), b.salary()));
Method reference (Java 8)list.sort(Comparator.comparingDouble(Employee::salary));

⚠ Interview Trap

A lambda can only capture local variables that are effectively final (never reassigned after initialization). Mutating a captured variable from inside the lambda body is a compile error, not a runtime one — this is asked constantly to check if you understand closures in Java are "capture by value of the reference," not true mutable closures like JavaScript.

Pattern Recognition

Any method parameter typed as a single-abstract-method interface (Runnable, Comparator<T>, Predicate<T>...) is a signal you can pass a lambda instead of writing a class.
💡 A lambda is just an unnamed method plugging into a functional interface's one open slot.

02. Built-in Functional Interfaces

java.util.function ships a small vocabulary of generic functional interfaces so you rarely need to declare your own. Every one of them boils down to "how many inputs, and is there an output?"

InterfaceAbstract MethodShapeExample
Predicate<T>boolean test(T t)T → booleane -> e.salary() > 80000
Function<T,R>R apply(T t)T → REmployee::name
Supplier<T>T get()() → TArrayList::new
Consumer<T>void accept(T t)T → voidSystem.out::println
BiFunction<T,U,R>R apply(T t, U u)(T,U) → R(a,b) -> a + b
UnaryOperator<T>T apply(T t)T → TString::toUpperCase
BinaryOperator<T>T apply(T t1, T t2)(T,T) → TInteger::sum, used by reduce()

Chaining with default methods

Predicate gives .and(), .or(), .negate(). Function gives .andThen() (run this, then that) and .compose() (run that first, then this). 
Predicate<Employee> isEng   = e -> e.dept().equals("Engineering");
Predicate<Employee> isRich  = e -> e.salary() >= 80000;
Predicate<Employee> target  = isEng.and(isRich);   // both must be true
// matches: Alice, Dave

⚠ Interview Trap

f.andThen(g) means "apply f, feed result into g" — f.compose(g) means "apply g first, feed result into f." They're mirror images, and interviewers love a one-line trick question swapping them.

Pattern Recognition

Need a boolean test → Predicate. Need a transform → Function. Need to produce a value from nothing → Supplier. Need a side effect with no return → Consumer. Need to combine two same-typed values → BinaryOperator (this is exactly what reduce() expects, pg 10).
💡 Count the inputs, check for an output — that tells you which functional interface you need before you even open the docs.

03. Method References

When a lambda's entire body is just "call one existing method," a method reference says the same thing more directly. There are four kinds:

#KindSyntaxEquivalent Lambda
1Static methodInteger::parseInts -> Integer.parseInt(s)
2Instance method of a particular objectSystem.out::printlnx -> System.out.println(x)
3Instance method of an arbitrary object of a typeEmployee::namee -> e.name()
4Constructor referenceArrayList::new() -> new ArrayList<>()

Kind 3 is the one that confuses people

Employee::name looks like a no-arg call, but as a Function<Employee,String> the arbitrary instance becomes the parameter: 
employees.stream().map(Employee::name)      // Function<Employee,String>
// is exactly:
employees.stream().map(e -> e.name())

⚠ Interview Trap

A constructor reference must match the functional interface's exact arity. Employee::new only compiles as a Supplier<Employee> if you'd otherwise call new Employee() with no args — if the record needs 6 fields, it instead matches a 6-argument functional interface, which usually means you need a custom one (Java only ships up to BiFunction).

Pattern Recognition

Read the lambda body. If it's only x -> SomeClass.method(x), x -> x.method(), or () -> new SomeClass() with nothing else — replace it with a method reference. If there's any extra logic (a conditional, an extra arg, string concatenation), keep the lambda.
💡 Method references aren't a different feature — they're lambdas whose body was already just "call this one thing."

04. Stream API Fundamentals

A Stream<T> is not a data structure — it holds no elements of its own. It's a pipeline description: a source, zero or more lazy intermediate operations, and exactly one terminal operation that actually pulls elements through and produces a result.

Common sources

SourceExample
Collectionemployees.stream()
ArrayArrays.stream(intArray)
Literal valuesStream.of("a","b","c")
Numeric rangeIntStream.range(0,5) / rangeClosed(1,5)
Infinite + limitStream.iterate(1, n -> n*2).limit(5)
GenerativeStream.generate(Math::random).limit(3)

Intermediate vs terminal: intermediate ops (filter, map, sorted, distinct, limit, skip, peek) return a new Stream and are lazy — they just get recorded. Only a terminal op (collect, forEach, reduce, count, findFirst, anyMatch...) actually runs the pipeline, element by element.

.stream()
→
.filter(...)
→
.map(...)
→
.sorted()
→
.collect(...)
StepWhat actually happens
Call .filter(...)Nothing runs — just records "there's a filter stage"
Call .map(...)Nothing runs — just records "there's a map stage"
Call .collect(...)NOW every element flows through filter → map → collect, one at a time, in one pass

⚠ Interview Trap

A stream can only be consumed once. Calling a second terminal operation on the same stream throws IllegalStateException: stream has already been operated upon or closed. If you need the data twice, build a fresh stream from the source collection each time.

Complexity

Element-wise stages fuse into one pass — O(n) total, same as an equivalent hand-written loop. Streams don't parallelize automatically; that needs .parallelStream() explicitly (pg 14).
💡 Nothing runs until a terminal operation is called — a stream is a recipe, not a result.

05. filter → map → collect, and flatMap

Dataset used across every stream page: 8 Employee(name, dept, salary, age, rank, skills) records.

Goal: names of every Engineering employee.

List<String> names = employees.stream()
    .filter(e -> e.dept().equals("Engineering"))
    .map(Employee::name)
    .collect(Collectors.toList());
StageContents flowing through

flatMap — when the element IS a collection

map on skills gives Stream<List<String>> (a stream of lists — one nested list per employee). flatMap flattens all those inner lists into a single flat Stream<String>. 
Set<String> allSkills = employees.stream()
    .flatMap(e -> e.skills().stream())   // List<String> → Stream<String>, then merged
    .collect(Collectors.toSet());
// {Java, Kafka, Spring, AWS, Excel, HR, Python, ML, Docker}

⚠ Interview Trap

map(Employee::skills) → Stream<List<String>> (5 boxes, each containing a list). flatMap(e -> e.skills().stream()) → Stream<String> (one flat stream of every skill). Mixing these up is the #1 flatMap interview mistake.

Pattern Recognition

Filter by a condition → filter+map+collect. Element contains a nested list/stream/Optional and you need ONE flat stream of the inner values → flatMap.
💡 map transforms one-to-one; flatMap transforms one-to-many and merges the many back into one stream.

06. sorted + distinct + limit/skip — "Nth Highest" Family

Problem: 2nd highest distinct salary. salaries = [95000, 80000, 60000, 95000, 70000, 55000, 90000, 75000] (note 95000 appears twice — Alice and Dave).

Optional<Integer> second = salaries.stream()
    .distinct()                    // remove duplicate 95000
    .sorted(Comparator.reverseOrder())
    .skip(1)                       // skip the 1st (highest)
    .findFirst();                  // take the next one
StageContents
source95000, 80000, 60000, 95000, 70000, 55000, 90000, 75000
after distinct()95000, 80000, 60000, 70000, 55000, 90000, 75000 (dup 95000 removed)
after sorted(reverseOrder)95000, 90000, 80000, 75000, 70000, 60000, 55000
after skip(1)90000, 80000, 75000, 70000, 60000, 55000
after findFirst()Optional[90000] ✅ — the 2nd highest distinct salary

The general recipe

"Nth highest/lowest, duplicates collapsed" always reduces to: distinct() → sorted() (ascending or reversed) → skip(N-1) → findFirst(). Want the top N instead of the Nth exactly? Swap skip(N-1).findFirst() for limit(N).

⚠ Interview Trap

Forgetting distinct() when the problem means "2nd highest distinct value" — without it, a tied top value silently becomes both the 1st and 2nd result. Also: distinct() before sorted() is cheaper (fewer elements to sort) — order your intermediate ops to shrink the pipeline as early as possible.

Complexity

distinct() is O(n) (hash-based). sorted() is O(n log n) — dominates the pipeline. skip/limit/findFirst are O(1) once the upstream work is done.

Pattern Recognition

"Nth highest/lowest", "top K", "unique values ranked" → this exact four-operation chain, every time.
💡 distinct → sorted → skip/limit → findFirst is the entire "Nth highest" pattern in one line.

07. Collectors I — groupingBy + Downstream

Problem: bucket employees by department, then aggregate each bucket.

Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::dept));
Key (dept)Bucket (List<Employee>)
Engineering[Alice, Bob, Dave, Heidi]
HR[Carol, Frank]
Finance[Eve, Grace]

The two shapes — memorize the signature, not the examples

groupingBy(classifier)
    -> Map<K, List<V>>               // default downstream is toList()

groupingBy(classifier, downstream)
    -> Map<K, X>                      // X = whatever the downstream collector returns
Every row in the table below is just "what is X?" for the second shape — once you can answer that, you can predict the return type of any groupingBy call before you write it.

Downstream collectors replace the default "collect into a List" with a smaller aggregate per bucket — pass it as the 2nd argument to groupingBy:

DownstreamReturnsExampleResult for "Engineering"
toList() (default)Map<K, List<V>>groupingBy(dept)[Alice, Bob, Dave, Heidi]
counting()Map<K, Long>groupingBy(dept, counting())4
summingInt(fn)Map<K, Integer>groupingBy(dept, summingInt(Employee::age))116 (30+28+32+26)
summingDouble(fn)Map<K, Double>groupingBy(dept, summingDouble(Employee::salary))345000.0
averagingDouble(fn)Map<K, Double>groupingBy(dept, averagingDouble(Employee::salary))86250.0
maxBy(comparator)Map<K, Optional<V>>groupingBy(dept, maxBy(comparingDouble(Employee::salary)))Optional[Alice]
mapping(fn, toList())Map<K, List<X>>groupingBy(dept, mapping(Employee::name, toList()))[Alice, Bob, Dave, Heidi]
filtering(pred, toList())Map<K, List<V>>groupingBy(dept, filtering(e -> e.salary()>=80000, toList()))[Alice, Bob, Dave]
collectingAndThen(d, finisher)Map<K, RR>groupingBy(dept, collectingAndThen(maxBy(comparingDouble(Employee::salary)), Optional::get))Alice (not Optional[Alice])
groupingBy(inner)Map<K, Map<K2, List<V>>>groupingBy(dept, groupingBy(rank)){1:[Dave], 2:[Alice], 3:[Bob], 4:[Heidi]}

collectingAndThen — post-process a collector's result

Wraps any collector and runs a finisher function on its output after collection completes — the collector's own return type doesn't have to be the final answer. Two use cases come up constantly: 
// 1. Unwrap the Optional that maxBy/minBy always produce, when you KNOW the group can't be empty
Map<String, Employee> topEarnerByDept = employees.stream().collect(
    Collectors.groupingBy(Employee::dept,
        Collectors.collectingAndThen(
            Collectors.maxBy(Comparator.comparingDouble(Employee::salary)),
            Optional::get)));                      // Map<K,Optional<V>> -> Map<K,V>

// 2. Make a collected list immutable — finisher doesn't have to change the TYPE, just the value
List<Employee> frozen = employees.stream().collect(
    Collectors.collectingAndThen(Collectors.toList(), Collections::unmodifiableList));

⚠ Interview Trap

Optional::get as the finisher is only safe because groupingBy never creates a key for an empty bucket — every group that exists had at least one element, so maxBy's Optional inside it is guaranteed present. Using the same Optional::get trick on a plain (non-grouped) stream().collect(maxBy(...)) over a possibly-empty stream is not safe — that Optional really can be empty.

Two-level grouping

Nest a groupingBy as the downstream of another to bucket by two keys at once: 
Map<String, Map<Integer, List<Employee>>> byDeptThenRank =
    employees.stream().collect(
        Collectors.groupingBy(Employee::dept,
            Collectors.groupingBy(Employee::rank)));
// {"Engineering": {1: [Dave], 2: [Alice], 3: [Bob], 4: [Heidi]}, ...}

⚠ Interview Trap — filtering() keeps the empty group, .filter() erases it

// filtering() runs INSIDE groupingBy — the key survives even if its bucket ends up empty
groupingBy(Employee::dept, filtering(e -> e.salary() > 200000, toList()))
// {"Engineering":[], "HR":[], "Finance":[]}   ← every dept key still present, empty lists

// .filter() BEFORE groupingBy removes elements from the source — a dept with
// zero survivors never becomes a key at all
employees.stream().filter(e -> e.salary() > 200000)
    .collect(groupingBy(Employee::dept))
// {}   ← no keys survive, because no employee passed the filter
If the requirement is "show every department, even ones with zero qualifying employees," you need filtering as the downstream — a plain upstream .filter() silently deletes those department keys.

⚠ Interview Trap

The Map returned by groupingBy is a plain HashMap — no guaranteed order, of keys or insertion. If you need insertion order or sorted keys, use the 3-arg overload with a map-factory: groupingBy(Employee::dept, TreeMap::new, toList()).

Pattern Recognition

"Group by X, then compute Y per group" (count, sum, average, list of names, max element) → groupingBy + downstream collector, every time. Need to keep every key even when its bucket empties out → filtering as the downstream, not an upstream .filter().
💡 groupingBy answers "bucket by key" — the downstream collector answers "what do I want to know about each bucket?" — and filtering vs .filter() decides whether an empty bucket still gets to keep its key.

08. Collectors II — partitioningBy, joining, toMap, teeing

partitioningBy — always exactly 2 buckets

Map<Boolean, List<Employee>> split = employees.stream()
    .collect(Collectors.partitioningBy(
        e -> e.salary() >= 80000));
// true  -> [Alice, Bob, Dave, Grace]
// false -> [Carol, Eve, Frank, Heidi]
Unlike groupingBy, the false key is always present even if empty — the map has exactly 2 entries, guaranteed.

joining — build a delimited String

String names = employees.stream()
    .map(Employee::name)
    .collect(Collectors.joining(", ", "[", "]"));
// "[Alice, Bob, Carol, Dave, Eve, Frank, Grace, Heidi]"

toMap — key/value pairs, with a merge function for collisions

Map<String, Double> salaryByName = employees.stream()
    .collect(Collectors.toMap(Employee::name, Employee::salary));
// works — every name is unique here

// if keys could collide, a 3rd arg resolves it:
Map<String, Double> maxSalaryByDept = employees.stream()
    .collect(Collectors.toMap(Employee::dept, Employee::salary,
        Double::max));   // keep the higher salary on key collision

⚠ Interview Trap

toMap(keyFn, valFn) with no merge function throws IllegalStateException: Duplicate key the moment two elements produce the same key. This is the #1 toMap production crash — always ask "can two elements collide on this key?" before skipping the 3rd argument.

teeing (Java 12+) — two collectors, one pass

Not part of Java 8 itself, but commonly grouped with the Collectors toolkit — worth knowing where the line is: 
var minMax = employees.stream().collect(Collectors.teeing(
    Collectors.minBy(Comparator.comparingDouble(Employee::salary)),
    Collectors.maxBy(Comparator.comparingDouble(Employee::salary)),
    (min, max) -> List.of(min.get(), max.get())));
// [Frank(55000), Alice(95000)] — computed in ONE pass, not two

Pattern Recognition

Exactly two outcome groups (yes/no) → partitioningBy. Build one joined string → joining. Need a lookup Map from a stream → toMap (always think about key collisions).
💡 groupingBy is for N buckets by any key; partitioningBy is groupingBy's simpler 2-bucket boolean cousin.

09. reduce() — The Fold Pattern

reduce is the most general stream operation: fold every element into a single running result. Everything else (sum, max, count, collect) can be expressed as a reduce — but use the specialized version when one exists, it reads clearer and is often faster.

OverloadSignatureWhen
1-argOptional<T> reduce(BinaryOperator<T> op)No sensible identity value; stream might be empty
2-argT reduce(T identity, BinaryOperator<T> op)Identity value exists (0 for sum, 1 for product)
3-argU reduce(U identity, BiFunction<U,T,U> acc, BinaryOperator<U> combiner)Result type differs from element type; required for .parallelStream()

Total salary, traced step by step (2-arg form, identity = 0):

StepEmployeesalaryrunning total = total + salary
1Alice950000 + 95000 = 95000
2Bob8000095000 + 80000 = 175000
3Carol60000175000 + 60000 = 235000
4Dave95000235000 + 95000 = 330000
5Eve70000330000 + 70000 = 400000
6Frank55000400000 + 55000 = 455000
7Grace90000455000 + 90000 = 545000
8Heidi75000545000 + 75000 = 620000
double total = employees.stream()
    .reduce(0.0, (sum, e) -> sum + e.salary(), Double::sum);
// equivalent, and preferred for numeric sums:
double total2 = employees.stream().mapToDouble(Employee::salary).sum();

// max salary via BinaryOperator.maxBy:
Optional<Employee> top = employees.stream()
    .reduce(BinaryOperator.maxBy(Comparator.comparingDouble(Employee::salary)));
// Optional[Alice] (first max wins ties — Alice appears before Dave)

⚠ Interview Trap

The 3rd argument (combiner) in the 3-arg overload is silently ignored in a sequential stream — it only matters for .parallelStream(), where partial results computed by different threads must be merged back together. Forgetting this exists is why parallel reduces sometimes give surprising results if the combiner logic is wrong.

Pattern Recognition

"Combine every element into one summary value" and no built-in collector fits → reduce. If it's specifically sum/min/max/count on numbers, prefer IntStream/DoubleStream's dedicated methods instead.
💡 reduce is the general-purpose fold — reach for the specialized sum()/max()/collect() first, and reduce only when nothing else fits.

10. Optional<T> — Null Safety

Optional<T> is a container that may or may not hold a value. It doesn't eliminate null — it forces the caller to explicitly handle the "no value" case in the type system, instead of finding out three calls later via NullPointerException.

Problem: find employee named "Zed" — doesn't exist.

Optional<Employee> found = employees.stream()
    .filter(e -> e.name().equals("Zed"))
    .findFirst();
// Optional.empty() — the stream produced zero matches
MethodBehavior
isPresent() / isEmpty()true/false check — isEmpty() added in Java 11
get()Throws NoSuchElementException if empty — avoid calling directly
orElse(fallback)Fallback value — always evaluated eagerly, even when present
orElseGet(() -> fallback)Fallback supplier — evaluated lazily, only when empty
orElseThrow(...)Throws a custom exception instead of NoSuchElementException
map(fn) / flatMap(fn)Transform the contained value, still wrapped in Optional
ifPresent(consumer)Run a side effect only if a value exists
ifPresentOrElse(consumer, runnable)Java 9+ — both branches in one call

⚠ Interview Trap

orElse(computeExpensiveDefault()) calls computeExpensiveDefault() every single time, even when the Optional already has a value — because Java evaluates the argument before calling orElse. orElseGet(() -> computeExpensiveDefault()) only invokes the supplier when actually needed. This is a very common perf/correctness trick question.

Pattern Recognition

A method that might legitimately find nothing (a search, a lookup, a parse) → return Optional<T>, never null. Don't use Optional for fields, method parameters, or collections — that's an anti-pattern the JDK team explicitly warned against.
💡 Optional is a signal in the type system that "this might not exist" — not a blanket replacement for every nullable variable.

11. Comparator — comparing / thenComparing / reversed

Java 8 added static/default methods to Comparator so multi-key sorts read as a declarative chain instead of a hand-written compare() method.

Goal: sort by dept (asc), then salary (desc), then name (asc) as the final tiebreaker.

List<Employee> sorted = employees.stream()
    .sorted(Comparator.comparing(Employee::dept)
        .thenComparing(Employee::salary, Comparator.reverseOrder())
        .thenComparing(Employee::name))
    .collect(Collectors.toList());

12. Reverse / Invert a Map — by Value

Flipping a Map<K,V> into a Map<V,K> (or Map<V,List<K>>) is the single most-reused building block in the next three pages — org tree, tiebreak sorting, and joins all start by looking a map's values up as if they were keys. The only decision that matters: are the values guaranteed unique?

Variant A — values are unique → toMap

Map<String, Integer> idByName = Map.of(
    "Alice", 101, "Bob", 102, "Carol", 103);

Map<Integer, String> nameById = idByName.entrySet().stream()
    .collect(Collectors.toMap(
        Map.Entry::getValue,   // old value becomes new key
        Map.Entry::getKey));   // old key becomes new value
// {101=Alice, 102=Bob, 103=Carol}

Variant B — values repeat → groupingBy

Map<String, String> nameToDept = Map.of(
    "Alice","Engineering", "Bob","Engineering",
    "Carol","HR", "Dave","Engineering", "Eve","Finance");

Map<String, List<String>> deptToNames = nameToDept.entrySet().stream()
    .collect(Collectors.groupingBy(
        Map.Entry::getValue,                                        // dept becomes new key
        Collectors.mapping(Map.Entry::getKey, Collectors.toList()))); // names bucket up
// {Engineering=[Alice, Bob, Dave], HR=[Carol], Finance=[Eve]}
QuestionIf yesIf no / unsure
Can two keys share the same value?groupingBy + mapping → Map<V, List<K>>toMap → Map<V,K> (1:1 only)

⚠ Interview Trap

Reaching for toMap out of habit when values aren't actually unique throws IllegalStateException: Duplicate key the instant two entries share a value (same trap as pg 9, resurfacing here because inversion is exactly where it bites hardest). When in doubt, default to groupingBy — a Map<V,List<K>> degrades gracefully to a 1-element list even when values genuinely are unique.

Pattern Recognition

"Reverse a map", "invert key/value", "look up the original key given a value" → toMap (unique values) or groupingBy+mapping (repeating values). This is step 1 of the Org Tree pattern on the next page.

Complexity

O(n) either way — one pass over the entry set, one insert per entry.
💡 toMap flips 1:1, groupingBy flips 1:many — pick based on whether values repeat, not on habit.

13. Org Tree from Map<Emp,Mgr> — Invert + DFS

Given: a flat Map<Employee,Manager> — every employee points to their one boss, and the root's manager is null. Task: print the org chart top-down, indented by depth.

EmpMgrEmpMgr
ABEA
B— (root)FC
CAGD
DBHC

Three steps — invert, find root, DFS

// Step 1: invert Map<Emp,Mgr> -> Map<Mgr,List<Reportee>>   (Variant B from pg 12)
Map<String, List<String>> mgrToReportees = empToMgr.entrySet().stream()
    .filter(e -> e.getValue() != null)
    .collect(Collectors.groupingBy(
        Map.Entry::getValue, LinkedHashMap::new,             // preserve sibling order
        Collectors.mapping(Map.Entry::getKey, Collectors.toList())));

// Step 2: root = the one entry with a null manager
String root = empToMgr.entrySet().stream()
    .filter(e -> e.getValue() == null)
    .map(Map.Entry::getKey).findFirst()
    .orElseThrow();

// Step 3: DFS, indent = depth
void dfs(String node, int depth, Map<String,List<String>> tree) {
    System.out.println(depth == 0 ? node : "  ".repeat(depth-1) + "--" + node);
    for (String r : tree.getOrDefault(node, List.of())) dfs(r, depth + 1, tree);
}

Output (B is root; indentation shows depth):

B
--A
  --C
    --F
  --E
--D
  --G

⚠ Interview Trap

A cycle in the input (A→B, B→A) sends the DFS into infinite recursion — guard with a visited set. A very deep tree (10k+ levels) blows the JVM's default stack via recursion — rewrite as an iterative DFS using an explicit Deque<Pair<String,Integer>>. Also plan for a forest (multiple null-manager rows) by collecting all roots, not just findFirst().

Pattern Recognition

"Flat parent-pointer map" + "print/traverse top-down" → invert once into parent→children (pg 12's Variant B), then DFS or BFS from the root. Same shape as RBAC role-hierarchy resolution or LDAP nested-group flattening.

Complexity

O(n) to invert + O(n) to visit every node once = O(n) total, where n = number of employees.
💡 Invert once, cache it — you can't traverse "top down" until you've flipped "who's my boss" into "who reports to me."

14. Sort Children by X, Tiebreak by Parent's Y

Given: Map<Manager,List<Reportee>>. Task: return every reportee across all managers, sorted by the reportee's age — ties broken by their manager's age. The trap: flattening the map naively throws away the manager link the tiebreaker needs.

PhaseWhatStream equivalent
A — attachPair each reportee with their manager (a "sticky note")flatMap(e -> e.getValue().stream().map(r -> Map.entry(r, e.getKey())))
B — sortPrimary: reportee age. Tiebreak: manager agesorted(comparingInt(reportee age).thenComparingInt(manager age))
C — peelDiscard the sticky note, keep only the reporteemap(Map.Entry::getKey)
List<Employee> sortedDirectReporteesByAge(Map<Employee, List<Employee>> orgChart) {
    return orgChart.entrySet().stream()
        .flatMap(e -> e.getValue().stream()
                       .map(r -> Map.entry(r, e.getKey())))          // (reportee, manager)
        .sorted(Comparator
            .<Map.Entry<Employee,Employee>>comparingInt(en -> en.getKey().getAge())
            .thenComparingInt(en -> en.getValue().getAge()))
        .map(Map.Entry::getKey)                                       // peel back to reportee
        .collect(Collectors.toList());
}

⚠ Interview Trap

Most candidates call orgChart.values().stream().flatMap(List::stream) first — that discards the manager link, and the tiebreaker becomes unimplementable one line later. Say out loud, before coding: "the sort key and the tiebreak key live at different levels of the input, so flattening must preserve both."

Second trap: if reportee age and manager age both tie, the result order looks "stable" but the input is a HashMap — iteration order was never deterministic to begin with. Add an explicit third tiebreaker (id/name); never rely on encounter order for correctness.

Pattern Recognition

"Sort children by their own field, tiebreak by parent's field" → flatMap into (child, parent) pairs before sorting, project back to just the child after. General rule: whenever a sort rule needs data outside the element itself, join it in before sorting.

Complexity

O(n log n), where n = total reportee count across all managers (dominated by the sort).
💡 Whenever a tiebreaker needs data outside the element, join it in before sorting and peel it off after — never sort what you've already flattened the context away from.

15. Join Two Maps by a Shared Key

Java has no SQL-style join operator, but streaming one map's entries and looking each value up in a second map — by a key domain they both share — reproduces an inner/left join in a few lines. This is the natural next step after Org Tree (pg 13) and the tiebreak pattern (pg 14): all three "reshape one map using another map (or itself) as a lookup."

Map<String, String> deptOfEmployee = Map.of(
    "Alice","Engineering", "Carol","HR", "Eve","Finance");
Map<String, String> headOfDept = Map.of(
    "Engineering","Dave", "HR","Frank", "Finance","Grace");

Map<String, String> employeeToHead = deptOfEmployee.entrySet().stream()
    .collect(Collectors.toMap(
        Map.Entry::getKey,                                      // employee stays the key
        e -> headOfDept.getOrDefault(e.getValue(), "Unknown")   // look up head via shared dept
    ));
Employeedept (join key)Department Head (looked up)
AliceEngineeringDave
CarolHRFrank
EveFinanceGrace

⚠ Interview Trap

Using plain headOfDept.get(dept) instead of getOrDefault/Optional means a dept missing from the second map silently poisons the result with null, which then NPEs several calls later, far from the actual join. Decide up front: should an unmatched row be dropped (filter before collecting) or defaulted (getOrDefault)? Don't let a silent null decide for you.

Pattern Recognition

"Two maps share a key domain and I need one combined view" → stream the left map's entries, look up into the right map by the shared key. This is exactly the mental model behind the Org Tree's manager lookup and the tiebreaker's manager-age lookup — a join is the general case, those two are joins against yourself.

Complexity

O(n) — one pass over the left map, each lookup O(1) because the right side is a HashMap. Using a List for the right side instead would make each lookup O(m), turning the whole join into O(n·m) — always pick a Map for the lookup side.
💡 A stream join is "for each entry on the left, look up the right side by the shared key" — put a Map on the right or the lookup itself becomes the bottleneck.

16. default/static Interface Methods & java.time

default methods — why they exist

Before Java 8, adding a method to an interface broke every class that implemented it. default gives the method a body right in the interface, so old implementors keep compiling unchanged. 
interface Greeter {
    String name();
    default String greet() {         // new in v2, doesn't break old code
        return "Hello, " + name() + "!";
    }
}
This is exactly how Collection.stream() was retrofitted onto every existing collection class without touching their source.

static interface methods

A factory/helper method that belongs to the interface itself, not any instance — Comparator.comparing(...) and Function.identity() are both static interface methods. 
interface MathOps {
    static int square(int x) { return x * x; }
}
MathOps.square(5);   // 25, called on the interface directly

⚠ Interview Trap — the diamond problem

If a class implements two interfaces that both define the same default method signature, it fails to compile until the class explicitly overrides that method and picks (or combines) an implementation with InterfaceName.super.method(). Java refuses to guess for you.

💡 default methods evolve interfaces without breaking old code; java.time fixes the old API by making every value immutable.

17. Interview Traps & Parallel Streams

⚠ Checked exceptions inside a lambda

Functional interfaces don't declare checked exceptions, so this does not compile: 
files.forEach(f -> Files.readAllLines(f));  // ✗ IOException is checked
Fix: catch and wrap locally, or write a small custom functional interface that declares throws Exception and wraps it yourself. 
files.forEach(f -> {
    try { Files.readAllLines(f); }
    catch (IOException e) { throw new UncheckedIOException(e); }
});

⚠ Stream reuse

Calling a 2nd terminal op on an already-consumed stream throws IllegalStateException. Rebuild from the source collection each time you need to traverse again.

⚠ Autoboxing in numeric pipelines

Stream<Integer> boxes every element. Prefer IntStream/mapToInt(...) for numeric work — avoids box/unbox overhead and unlocks .sum()/.average()/.max() directly.

⚠ Mutable state captured in a lambda

Lambdas can only capture effectively final locals, so people reach for a 1-element array or AtomicInteger as a workaround to "mutate" state inside forEach: 
// anti-pattern — fighting the model instead of using it
int[] total = {0};
employees.forEach(e -> total[0] += e.salary());   // ✗ works, but not idiomatic

// idiomatic — let reduce/collect own the accumulation
double total2 = employees.stream().mapToDouble(Employee::salary).sum();  // ✓

⚠ .parallelStream() pitfalls

  • Shared mutable state (e.g. adding to a plain ArrayList from forEach) races across threads and silently corrupts data — use collect(), which handles thread-safety internally, never manual accumulation.
  • Element order is not guaranteed to be preserved unless the downstream collector/terminal op explicitly requires it.
  • For small N or I/O-bound work, thread coordination overhead usually costs more than it saves — parallel streams pay off for large, CPU-bound, stateless, associative operations only.
